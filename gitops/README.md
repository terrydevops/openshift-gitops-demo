# OpenShift GitOps Reference: Platform / Application Separation

A reference GitOps layout for OpenShift (Argo CD) demonstrating **platform-team vs
application-team separation**, an **App-of-Apps** bootstrap, and a database managed
by an **Operator/CRD** (CloudNativePG) instead of a hand-rolled StatefulSet.

> Edit locally → push to Git → **Argo CD pulls and syncs**. Both the platform and the
> application are managed by Argo CD ("GitOps all the way down"). The layout is
> environment-agnostic — no cluster-, namespace-, or cloud-specific values are hard-coded.

## Layout
```
gitops/
├── bootstrap/
│   └── root-app.yaml              # The ONLY manual step: apply this once after Argo CD is installed
├── platform/                      # Owned by the platform team (cluster-admin)
│   ├── operators/operators.yaml   # OpenShift GitOps + CloudNativePG Subscriptions (managed by OLM)
│   ├── tenants/app-a/tenant.yaml  # Namespace + ResourceQuota + LimitRange + RoleBinding + deployer SA
│   └── argocd/
│       ├── projects.yaml          # AppProjects: platform (privileged) / app-a (restricted + impersonation)
│       ├── applications.yaml      # Child Applications: operators / tenants / app-a
│       └── argocd-rbac-cm.yaml    # Argo CD RBAC (who can operate which Applications)
└── apps/app-a/                    # Owned by the application team (admin within app-a only)
    └── Helm chart: CNPG Cluster CRD + webapp (wired to the CNPG-generated secret)
```

## App-of-Apps bootstrap chain
```
apply bootstrap/root-app.yaml (once)
   └─ root syncs platform/argocd/ →
        wave -1: AppProjects (platform, app-a)
        wave  0: Applications operators, tenants
        wave  1: Application app-a
              └─ each child Application then reconciles its own content
```

## Permission separation (platform vs application) — three layers
| Layer | Mechanism | File | Purpose |
|------|-----------|------|---------|
| 1 | **AppProject** | projects.yaml | Restricts what an Application may deploy (app-a: no cluster-scoped resources) |
| 2 | **Argo CD RBAC** | argocd-rbac-cm.yaml | Restricts which team (group) can operate which Applications |
| 3 | **Impersonation SA** | projects.yaml + tenant.yaml | Argo applies app-a as a namespace-scoped SA, not the default cluster-admin |

> Layer 3 requires Argo CD ≥ 2.13 with `application.sync.impersonation.enabled: "true"` in `argocd-cm`.

## Operator (provides capability) vs CRD (consumes capability)
The platform team installs the **CloudNativePG Operator**; the application team simply
writes a namespaced **`Cluster` CR** to get a PostgreSQL instance with HA/backups.
Connection credentials are generated by the operator into a Secret (`<cluster>-app`) —
**no plaintext passwords in Git**.

## Notes
- `repoURL` points at this repository; adjust if you fork it.
- The CloudNativePG channel in `operators.yaml` should be verified before install:
  `oc get packagemanifest cloudnative-pg`.
- This repo intentionally contains **no secrets**. Database credentials are generated
  in-cluster by CloudNativePG; application config holds only non-sensitive values.
